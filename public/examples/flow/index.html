The flow

    Show

    Turystack, end to end

    A product starts as a design file, a briefing and a conversation, and ends as tasks whose every id is tied to the test that proved it. What follows is that path, with the branch at each step and the check that holds it.

    The step numbers on this page are the run order. The harness's section files keep their own names: the blueprint is 04-blueprint-bootstrap.md and runs before 03-uiux-bootstrap.md.

    Law skills

    Written by Turystack, rewritten on every install, never edited by a project.

    turystack-harness · -proof-mode · -architecture-pattern · -modeling · -backend-pattern · -frontend-pattern · -frontend-primitives-pattern

    Project skills

    Materialized once under the project's name and its own from then on. This is where the product's decisions live.

    <project>-blueprint · <project>-uiux

    The runner

    Runs the ladder and the structural checks the skills bind to, and emits the report whose verdict is computed.

    @turystack/proof-mode-gates → turystack-proof

    The repository exists

    Optional, and it decides things the blueprint will later assume. A project that already exists skips it — the bootstrap below is not optional either way. 

    turystack create api my-api     NestJS, one audience or several
turystack create web my-web     React, Vite, TanStack Router, generated SDK

    Variants

    Shapesingle · multi-audience — one API surface per audience, each with its own generated SDK
    Modulesdatabase · logger · cache · lock · rate-limit · publisher · storage · iam · observability · scheduler · social-auth
    Dependencieslocal file: links while the libraries are being developed, or published versions
    Brownfieldnothing to scaffold; the blueprint is still generated complete, with the running product as one more source
    Monorepo@acme/web and @acme/api are one project: the scope names it, and they share one blueprint

.claude/turystack.json      { "project": "acme", "skills": { … } }
.claude/skills/             the law, plus acme-blueprint and acme-uiux

    Every session starts here

    turystack-harness reads the disk — the manifest, the two project skills, the board — and says which of two modes this session is in. It never takes that from the conversation. 

    read .claude/turystack.json → <project>-blueprint → <project>-uiux → board/tasks.json

  missing, or every section still unfilled  →  BOOTSTRAP   (run order 03 → 05: blueprint → uiux → board)
  both answer                               →  ROUTINE     (run order 07)
  -spec and no -blueprint                   →  turystack skills --migrate-spec

    Variants

    Partly filledroutine, with a known hole: the first task that needs the empty section stops there and asks
    No manifestfalls back to the shape — the folders ending in -blueprint and -uiux
    gate:bootstrap-complete gate:spec-unfilled gate:uiux-unfilled
    Until step 05 has produced a board, no implementation runs. Not a scaffold, not “just the login screen”. The exception people reach for is the one that costs the most: a screen built before the blueprint decides what it does, kept because it works, and maintained afterwards as the reference for how screens are built here.

    A conversation becomes the blueprint

    Not extracted from the design and not inferred from the code. The design, the briefing and the docs are where it starts; the harness proposes and a person decides each answer. It is generated complete — every domain, its rules, model and flows — and what no source says keeps its marker and becomes a question, never a guess.

    Section file: 04-blueprint-bootstrap.md

    glossary → actors & conventions → domains, each with its id prefix
→ per domain: entities & states → rules → model → flows
→ cross-domain rules → capabilities with their acceptance criteria → erd
    • Propose what the sources only imply as a checklist per domain, the evidence on each item. Only what a person accepted is written.
    • List what no source says as questions. Each one stays an unfilled marker until someone answers it.
    • Review it whole before the sweep starts: every domain's four pages, the glossary, the conventions, the ERD, the cross-domain rules.

    Every decision leaves with an id of the domain that owns it

    SALES-AC-nan acceptance criterion, Given / When / Then
    SALES-R-na rule of the domain — an invariant or a validation
    SALES-EVN-na published event, and every handler that reacts to it
    SALES-JOB-nsomething that runs on a clock
    XD-R-na rule no single domain owns
    UX-DR-nwhat a design obliges
    TC-na test case a task will be proved by

    The design becomes the UI/UX skill

    The sweep runs after the blueprint, so every screen is read against words, actors and states that already exist: a label that disagrees with the glossary is a question, not a synonym.

    Section file: 03-uiux-bootstrap.md

    • Resolve the source. A file someone else can open again in six weeks, not “the Figma the designer shared”.
    • Sweep it, five readings at once. Tokens · layout · copy · component mapping · surfaces and their states.
    • Propose what the design only implies as a checklist, item by item. Only what a person accepted becomes a rule.
    • Write one theme per design system — tokens, then the slot, then the variant.

    Exports onlytokens from a token export or asked for; a state nobody exported is recorded as missing, never as absent

    Several design systemsaudiences drawn apart stay apart: one token set, one theme and one component mapping each. Merging them is irreversible in practice
    Missing slota component the library cannot theme is a gap in the library — a task before the surface that needs it, never a structural selector in the theme
    gate:theme-per-system gate:theme-override-shape gate:theme-in-sync gate:token-scheme-parity gate:design-export gate:design-requirement-ids manual · the checklist is answered by a person

    The blueprint becomes a board

    Derived from the blueprint's ids, never from the screens. One task per thing that can be proven — which is the same unit the delivery harness slices against. The board lives inside the blueprint and is continuous: nothing is deleted, an obsolete task is superseded and names its successor, and a done task is final — a change that touches it is a new task. 

    capability  SALES-AC-n   → one task per group of criteria that ships together
rule        SALES-R-n    → its own task where no capability already carries it
event       SALES-EVN-n  → the publication with its capability; each handler its own task
schedule    SALES-JOB-n  → always its own task
cross-domain XD-R-n      → the task where the domains meet
missing component        → a react-web task first, named in dependsOn

    A task is lean — what a person validates, never the code

    Intentone sentence: who does what, and what follows
    Impactdata · rules · operations · effects · screens · scheduled — no methods, classes, paths or hooks
    Caseswritten from the blueprint, one per thing checked, each naming the id it proves

    Two approvals before it reaches doing

    Plana person approves the impact — the data, rules, operation, effects and screen this change should have
    Casesa person corrects, deletes, and adds the cases only they know about
    tasks.json changed → npx --package @turystack/proof-mode-gates@^3.0.0 turystack-proof board --write .claude/skills/<project>-blueprint
    gate:board-covers-spec gate:board-pages gate:task-cases gate:board-continuous gate:task-shape

    One task, fixed phases, one report

    With the blueprint reviewed and a board derived, implementation is a loop with no product decisions left in it. The phases are fixed; which ones run is derived from the task's impact; turystack-proof-mode runs each one end to end, gated before the next. 

    take a task            plan and cases approved → open → doing
resolve its ids        every id opens to a row in the blueprint, or it goes back
data                   tables, enums, the migration          turystack-modeling
domain                 entities, guards, use-cases, rules    turystack-backend-pattern
routes                 controllers, permissions, OpenAPI     turystack-backend-pattern
async                  events, handlers, schedules           turystack-backend-pattern
contract               the SDK regenerated with Kubb         turystack-frontend-pattern
frontend               screens from react-web + the hooks    turystack-frontend-pattern
close                  delivery appended, history → done, pages regenerated

    Which phases the impact implies — each shows evidence or n/a with a reason; the others may be omitted

    datadata
    rulesdomain
    operationsdomain · routes · contract
    effectsdomain · async
    scheduledasync
    screenscontract · frontend

    The ladder, after every slice — not once at the end

    format → lint → typecheck → structure → test → coverage → e2e → visual

    It stops at the first red rung. A rung that goes red on a fifty-line slice names the change that broke it; the same rung on a finished task names nothing, and the next twenty minutes are bisecting.

    Variants

    Backend-onlya rule, a handler, a schedule — frontend is n/a, with its reason
    Frontend-onlya surface over an operation that already ships: data to async are n/a, contract shows the SDK is current
    Full-stackevery phase in order — the SDK is generated from the published contract, so a frontend built before it is built against a shape nobody published
    Missing componentreact-web lacks it: a task under frontend-primitives, named in dependsOn; the screen's task is blocked until it is delivered
    Missing decisioneverything that does not depend on it proceeds; the branch that does stops; the answer returns as an id in the blueprint
    Case turns out wrongback to the person who approved it. Deleting it in the commit that could not make it pass is the failure this whole step exists to prevent
    gate:plan-approved gate:cases-approved gate:phase-evidence gate:case-test-link gate:rule-id-coverage gate:spec-test-link gate:required-captures gate:contract-delta gate:board-report-linked gate:no-bypass

    Every session after that

    The harness states the mode, lists what is open, and asks which of three things this session is. It does not choose for the person, and it does not start coding because the last session was coding.

    Implement a task from the board, on a named surface → ends in a delivery appended to that task
    Audit the ids the blueprint declares against the deliveries that claim them → ends in a difference, and tasks for it. Never in an edit to the blueprint that makes the difference disappear
    Hunt a symptom → ends in an id: the criterion that was violated, or a new one written with the person who owns it

    A bug fixed with no id is a change nobody can audit, and it returns as a “regression” that was never a regression — it was a behaviour nobody had decided, twice.

    Every law names a gate — a check the runner implements, or manual. The distance between what the tables claim and what exists on disk is the backlog; the manual share is not a backlog at all, but the part of the law a machine was never going to check. A report prints both, which is what makes its green readable.
